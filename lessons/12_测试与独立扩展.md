## 2. 测试写法

```rust
#[cfg(test)]              // 只在 cargo test 时编译
mod tests {
    use super::*;

    #[test]
    fn 空列表从1开始编号() {
        assert_eq!(next_id(&[]), 1);
    }
}
```

常用断言：

```rust
assert_eq!(a, b);      // 相等，失败时会把两边的值都打出来
assert!(条件);          // 为真
assert!(result.is_err());   // 应该失败
```

跑测试：

```bash
cargo test              # 全部
cargo test next_id      # 名字里含 next_id 的
```

## 3. 测什么

测**边界**，不测显而易见的东西：

- 空列表
- 编号不存在
- 编号不是数字
- 存盘再读回来，数据一致（往返测试）

## 4. 任务 A：补测试

在 `src/store.rs` 底部加 `#[cfg(test)] mod tests`，至少覆盖：

1. `add` 之后 `len()` 加 1，新任务 `done == false`
2. `next_id` 在空列表上返回 1，在 `[1,2,5]` 上返回 6
3. `finish` 一个不存在的编号返回"没找到"，且不崩溃
4. 存盘再读回来，任务条数和完成状态都一致


## 5. 任务 B：独立加一个功能（毕业考）

**没有标准答案，自己做完。**

让 `list` 支持只看未完成的：

```bash
cargo run -- list --pending
```

要求：
1. 参数解析要认 `--pending`，不给就还是显示全部
2. 不认识的选项（比如 `--pendign`）要报错提示，不能默默忽略
3. 至少为它加一个测试
4. `cargo test` 全绿

做完之后，回答这三个问题（写下来）：

- 你改了哪几个文件？为什么是这几个？
- 如果以后还要加 `--done`（只看已完成），要改的是同样这几处吗？
- 你加的测试，在哪种情况下会失败？

能答上来，就说明你不只是抄通了，而是理解了这个程序的结构。
